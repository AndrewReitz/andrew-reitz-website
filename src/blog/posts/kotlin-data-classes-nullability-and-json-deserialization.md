Kotlin has an amazing feature! Nullable and non-nullable types built into the language. The Kotlin compiler will error out if you try to do something on a nullable type that you shouldn’t, otherwise with a non-nullable type you know that it cannot be null and go on your merry way. This is a huge improvement from Java development where we are used to the dreaded `NullPointerException`.

I’m not going to spend too much on nullable and non-nullable types since you can read about it in the official Kotlin documentation, and instead, I would like at some possible issues of going full Kotlin data classes, specifically when it comes to JSON deserialization.

First, let’s look at a data class.

`data class Person(val name: String, val age: Int)`

Really simple, but really efficient. This class is immutable and does not allow null for the name parameter. It automatically creates toString, hashCode, and equals methods. In Kotlin, if you try to pass a null value to name, you’ll get a compiler error

`val nullPerson = Person(null, 10)` &gt; Null can not be a value of a non-null type String

Pretty cool, but what happens if we try to do the same thing in Java? Well Java’s compiler doesn’t know about non-nullable types. The Kotin compiler does, however, annotate the property with `@NotNull` (from the generated bytecode) so you can get warnings from IDEs (it really pays to have an IDE company make a language).

`Person person = new Person(null, 10);`

For completeness, I left everything in that snippet. There’s a lot of code we don’t care about, but even if we remove that, we save a lot of keystrokes by using Kotlin’s data classes rather than trying to make our own immutable class in Java.

Now, a big problem in Android projects is we do lots and lot of serialization of JSON data. A huge win against the dreaded NP is [AutoValue](https://github.com/google/auto/tree/master/value) in combination with [AutoValue Gson Extension](https://github.com/rharter/auto-value-gson) (or any of the other JSON plugins). AutoValue is an annotation processor that creates immutable classes based off of abstract class you provide. AutoValue is a bit more typing than the data class we just looked at but Produces a similar result.
``@AutoValue  
**public** **abstract** **class** **Person** {  
  **public** Person **create**(String name, **int** age) {  
    **return** **new** AutoValue_Person(name, age);  
  }  
  **public** **abstract** String **name**();  
  **public** **abstract** **int** **age**();  
}``

Because only the abstract class is exposed in order to use this with a JSON serialization library, type adapters need to be created. Luckily for us, an extension to AutoValue, AutoValue Gson was been created. Simply adding another static method to our abstract person class, and giving Gson the type adapters created by AutoValue Gson we are ready to go (see AutoValue Gson docs for an example). Now, this is definitely more work than the Kotlin data classes which can be used out of the box, but AutoValue Gson actually uses the constructors of the auto-generated class. This is an important difference. See, Gson like many popular JSON serialization libraries use some tricks to be able to set values of final fields at runtime, thus bypassing all of the null checks that are put in place.

Don’t believe me, check out this snippet of code.
``val person = Gson().fromJson(&#34;{\&#34;name\&#34;:null,\&#34;age\&#34;:40}&#34;, Person::class.java)  
println(person)``

Does this compile? Of course, the Kotlin compiler has no idea what Gson is doing, and it shouldn’t have to. When it is run `Person(name=null, age=40)` is printed out. If you try to access and use name what happens? Well, adding`println(person.name.toUpperCase())` will throw `kotlin.TypeCastException: null cannot be cast to non-null type java.lang.String`. This is a `RuntimeException`, which completely defeats all of the checks the Kotlin compiler does for us! Also, this leads to some false sense of security, when you look at the code, you would assume that name cannot and never will be null so you never think to check otherwise. At least in Java, you can reasonably assume anything can be null.

In this simple example, we can easily see what the problem is and make corrective actions, but when you’re dealing with an API that you have little to no control over, with hundreds of model objects this can become a real burden. Imagine you’re working with an API that is poorly documented or is even documented perfectly, but someone missed that a value changed to nullable from V1 to V2. If the value is generally not null from the API or is not used frequently, it can be deserialized to the object and not noticed for a very long time. All of a sudden a user ends up with value as null at the only screen in your app that uses that value and boom `RuntimeException`.

You see the exception in your crash reporting tool but have a really hard time reproducing it since for you the value is never null (you probably will also scratch your head wondering how a non-nullable type is null). After some more digging into it, you realize the API must be sending the value as null, and update your code to better manage this. Lots of effort for something so simple!

If instead of the data class AutoVale was used, as soon as the value we thought could not be null become null we would have seen the crash every time the page loads (hopefully in your staging environment by your QA rather than in prod) and make a quick PR to update the value to be annotated as nullable and handle that it can be null throughout the codebase. A much faster solution because you know at the moment the server sends a null value to you that you are getting a value you didn’t expect. It’s much better to fail as soon as something is out of the ordinary so that it doesn’t go unnoticed and fixed.

So, inculcation I would recommend using AutoValue even in Kotlin projects for values that are serialized to and from JSON. You can even use AutoValue in Kotlin to get the added benefit of nullable and non-nullable types!
``@AutoValue  
abstract class Person {  
    companion object {  
        fun create(name: String, age: Int): Person {  
            return AutoValue_Person(name, age)  
        }  
    }  
    abstract fun name(): String  
    abstract fun age(): Int  
}``
